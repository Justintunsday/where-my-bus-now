# Live Activity background predictions and deployment

## Cause and implemented path

The previous host injected a nil push registrar, requested activities with no push token, and refreshed ETAs from a scene-bound foreground task. Suspension cancels that task and termination removes the app process. A system-rendered countdown can continue showing time passing, but cannot obtain changed operator predictions. No widget timer or background-mode entitlement fixes that distinction.

This revision implements an independent service in `server/live-activities` and wires its client into AppState through `LIVE_ACTIVITY_SERVER_URL`. When configured, a supported route requests ActivityKit `.token`; every token emission is uploaded. The service polls the operator independently of the app, constructs the exact Swift ContentState, and sends ActivityKit `update` or `end` pushes over APNs HTTP/2. Apple delivers directly to the system Live Activity while the app is suspended or absent, subject to delivery policies, connectivity and budgets. This is push-to-update, not ordinary silent notifications or push-to-start. User-selected tracking remains required.

**Implementation is supplied; live deployment and real APNs delivery are separate acceptance gates.** With an empty endpoint the unsigned build remains explicitly foreground-only. Do not call deployment or background delivery verified from a simulator countdown, local mock, or an APNs HTTP 200 alone.

## Client lifecycle

- The host includes the Push Notifications capability and `aps-environment` entitlement. Debug defaults to `development`/sandbox; Release defaults to `production`. Signing profiles and the configured service must agree. The widget needs no ordinary remote-notification background mode or push entitlement for ActivityKit rendering.
- `BusActivityRemoteConfiguration` validates the public HTTPS endpoint, generates a random installation credential, stores it in this-device-only Keychain after first unlock, and enrolls an installation-scoped anonymous session. No `.p8`, server encryption key, or shared bearer secret is embedded in the app.
- `HTTPBusActivityPushRegistrar` uses authenticated PUT/DELETE. `BusActivityPushCoordinator` observes all rotating per-activity tokens, persists monotonic upload versions and revocation IDs, cancels obsolete tasks, and retries registration at 0/1/2/4/8/16 seconds. Tokens are not persisted in preferences. A late obsolete upload cannot replace a newer server token. Relaunch re-reads the current token and reinstalls async observers.
- Registration status distinguishes pending, accepted and failed. `updateSource: push` identifies a snapshot actually received from the service. The Today card separately marks expired predictions and displays the last successful timestamp.
- `contentUpdates` keeps in-app tracking synchronized with system-received snapshots. On resume, ArrivalSession adopts the newer system state before requests; a failed local request cannot overwrite a fresh server snapshot. A newer successful foreground fetch can replace it.
- Stop/switch revokes the old subscription. The Lock Screen end intent runs in the host, ends immediately, then attempts one bounded revocation request. If the app cannot complete revocation, durable known IDs retry on reconciliation; server TTL and APNs invalidation bound remaining work. Dismissing an activity while the host is absent may only be observed through APNs invalidation or on resume; no guaranteed dismissal callback is assumed.
- Server adapters support Hong Kong KMB, Citybus, NLB, GMB, MTR, MTR Bus and Light Rail, plus hosted CheLaile bus routes. Ferries, AMap-only data, legacy mainland sources and metro realtime remain explicitly foreground-only. Existing regional browsing, schedules and ETA functions continue to use their existing providers. Older saved mainland targets without `realtimeCityID` must be reopened through their route to acquire the metadata before remote tracking.

## Service implementation

Node 24.15+ uses built-in HTTP, HTTP/2, crypto and SQLite; there are no runtime npm dependencies. `compose.yml` supplies an always-running container and persistent volume. **Run exactly one replica per SQLite volume.** An in-process worker guard prevents overlapping batches; this is not a distributed lease implementation. Scale beyond one process only after migrating to transactional shared storage/leases. `docs/activity-subscriptions.sql` is an earlier PostgreSQL migration design, not the schema used by this service.

The authenticated API enrolls installation credentials as hashes, scopes subscriptions by installation/activity ID, limits request size/rate and active subscriptions, validates the selected transit identity against provider metadata, and caps every trip at one hour. Tokens are AES-256-GCM encrypted at rest with a deployment key. Rotation versions reject obsolete writes. DELETE creates a tombstone even if it arrives before PUT; ended records clear tokens, targets and snapshots, and tombstones expire after 48 hours. Credential records without subscriptions expire after 30 days and can enroll again from Keychain.

The single worker checks due subscriptions every five seconds, fetches each full target once per batch, bounds concurrency to eight, and schedules successful fresh updates every 60 seconds. A successful fetch extends freshness by at most 90 seconds and never beyond the arrival. Available source timestamps are checked for stale operator caches. Changed arrival times replace the prediction; explicit canceled/arrived/departed entries are filtered, with a future successor selected when present. An empty board or expired prediction is unavailable, not evidence that a bus physically arrived or service ended; monitoring continues for subsequent departures. Explicit terminal status without a successor, permanent identity mismatch and the one-hour expiry send a final `end` event.

Failures preserve last successful clock history and its timestamp, invalidate freshness and send a stale network state. APNs transport/429/5xx/auth errors back off from 15 seconds up to five minutes, without recording failed delivery as fresh state. APNs 410/invalid-token responses revoke the token. Before and after asynchronous work, generation/revocation checks prevent obsolete work from being saved or sent after an already-observed revocation; an HTTP/2 request already in flight cannot be recalled.

APNs uses an ES256 P-256 JWT cached for 50 minutes, persistent environment-specific HTTP/2 connections, `apns-push-type: liveactivity`, `<host bundle ID>.push-type.liveactivity`, priority 5 and short expiration. Every message contains an integer monotonic `timestamp`, `event`, full `content-state`, and `stale-date`. End messages include `dismissal-date`. Unix seconds match Swift Codable; a generated Node payload is decoded by the Swift CI contract test. No alert payload or priority-10 polling is used. A 60-second server schedule is **not a promise of 60-second delivery** on devices. Frequent-update entitlement is deliberately not enabled.

## CheLaile and Hong Kong infrastructure

The upstream `Justintunsday/chelaile-api-server` was inspected at `37cdb4edec8a3120219b97b396ded83fc2b297b4` (2026-10-13). Its Bun server and Cloudflare Worker expose query routes including `/v1/lines/detail` and `/v1/lines/realtime`; they have no durable activity subscriptions, scheduling or APNs sender. Reuse it as a mainland query upstream. The new service resolves physical stop IDs to the line-station `sId`, station order and **WGS-84** coordinates from line detail. AMap IDs are never passed to CheLaile. Stable app provider IDs can contain administrative adcodes; `realtimeCityID` carries the distinct CheLaile citycode.

Hong Kong requires its own adapters: the daily hk-bus-crawling database validates the complete route variant, canonical stop occurrence and each operator's actual stop ID. Each operator API has separate direction/sequence/time semantics. Full dates and explicit Hong Kong timezone handle cross-midnight arrivals. Ferry schedules are not presented as fresh real-time pushes. No upstream repository or hosted query service was modified or deployed by this PR.

## Deploy and configure

1. Provision an always-running Docker host with HTTPS ingress, outbound HTTP/2 port 443 to APNs, and access to the listed transit APIs. Stateless Vercel requests or an ordinary cron alone cannot run this worker. Back up the SQLite volume and encryption key together; never run two replicas against that volume.
2. Copy `.env.example` to `.env`. Set Team ID, Key ID, actual signed host bundle ID, one APNs environment, and a cryptographically random 32-byte encryption key (64 hex characters). Mount the matching APNs `.p8` at `secrets/AuthKey.p8`, readable by the container's node user. Keep it out of git. Sandbox and production must use separate service instances, volumes, endpoints and correctly scoped Apple keys.
3. Run `docker compose up --build -d` from `server/live-activities`. Map public TLS ingress to its loopback port 8080. `/health` is API liveness; monitor worker operation and APNs acceptance separately. Add edge enrollment rate limits, request limits and abuse protection appropriate to deployment scale. Installation credentials scope ownership but do not attest an authentic App Store install; add App Attest before a large public rollout. Do not log Authorization headers, activity tokens or precise boarding targets.
4. Set `LIVE_ACTIVITY_SERVER_URL=https://your-service.example` in the host target's Xcode build settings. No `/v1` suffix: the client adds it. Set `APNS_ENVIRONMENT=development` for sandbox development signing or `production` for distribution. Enable Push Notifications on the App ID, regenerate provisioning, and sign both app and embedded extension with compatible identifiers/team. For CI unsigned artifacts, repository variable `LIVE_ACTIVITY_SERVER_URL` can supply the public endpoint; the artifact still needs correct signing before use.
5. `npm test` validates service behavior without credentials or Apple delivery. CI additionally builds the Docker image, decodes server state in Swift, compiles simulator/app extension, archives device app, verifies embedding and emits an unsigned IPA. Keep secrets in the deployment's secret manager, never GitHub artifact contents.

## Verification gates and current limits

| Evidence | What it establishes |
| --- | --- |
| Node fixtures + durable SQLite/restart tests | Independent provider work, identity validation, rotation/revocation, expiry, failures and successor state |
| Local HTTP/2 APNs receiver + cryptographic verification | Real sender code, ES256 signature, required headers and payload; **not Apple acceptance/delivery** |
| Node-generated JSON decoded by Swift | Exact cross-language ContentState serialization and whole-minute calculation |
| Simulator UI tests/screens on iOS 17, 18, 26 | Native controls, stale display, digits, navigation, classic fallback/glass rendering and actual system Island layout |
| Unsigned archive/IPA | Compilation and embedded extension packaging; **not installability or push provisioning** |
| Deployed service + signed physical device | Still required for APNs sandbox/production acceptance and visible background/terminated-app updates |

On a signed physical device: start tracking, record the system token/registration securely, background and lock the device, and verify that a **new arrivalEpoch/updatedEpoch** from the operator arrives without reopening. Repeat with the app terminated, changed ETA, cancellation with/without successor, cross-midnight departure, stale/drop/offline delivery, resumed local failure, route switch, token rotation, Lock Screen stop and system dismissal. Verify native iOS 26 light/dark glass and Reduce Motion/Transparency on hardware. APNs accepts pushes independently of whether the device displayed them; inspect device ActivityKit logs alongside server acceptance. Keep all identifiers/tokens private in diagnostic captures.
