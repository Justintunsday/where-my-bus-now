# Bus arrival Live Activities: implementation and deployment

## Shipped client behavior

The host app starts a user-selected, exact route/direction/service/boarding-stop activity with `ActivityContent`. `NSSupportsLiveActivities` and the `busnow` URL scheme are in the host plist. The embedded `BusArrivalWidget.appex` renders Lock Screen and all Dynamic Island families. Shared attributes, Unix-second content state, localized content and an end intent belong to both targets. No App Group is needed because the widget renders ActivityKit-supplied content; it does not read bookmarks or fetch data.

There is one tracked trip at a time. A new request must succeed before the previous activity ends. The manager restores existing activities, observes system state changes, reconciles dismissals and coalesces foreground requests with on-screen ETA sessions. Predictions expire after the earlier of 90 seconds and their predicted arrival time. Countdown text is system-rendered; it is not a new ETA request. WidgetKit checks `context.isStale` and shows an explicit refresh indication. A failed request replaces the live countdown with offline/unavailable status, retains the last clock times, and preserves the last successful timestamp. Empty provider results show no further departures; explicit cancellation/arrival/departure removes the countdown and ends tracking unless a new valid future bus exists. Only a new provider snapshot can select the next bus. An activity older than one hour ends when the app next runs in the foreground. The system can end it earlier and applies its own maximum lifetime when the app is suspended.

Manual ending is available in the app, Settings and the Live Activity button (`LiveActivityIntent`, included in both targets). Deep links encode the complete provider identity; the app validates the scheme, payload size, region, provider, operators, bound dictionary, service type, line ID, source, stop ID and sequence before displaying ETA. A changed route is never silently remapped to a same-number route.

**Default update mode is local foreground only.** `AppState` injects no registrar, so `supportsRemoteUpdates` is false and `pushType` is nil. The optional remote client path is implemented, but is inactive until an authenticated registrar is injected. There is no deployed registration service, background polling, push-to-start or frequent-update entitlement. ActivityKit and WidgetKit UI previews are available without an APNs service. Signed-device lifecycle/presentation still requires verification.

## Existing backend assessment

This repository includes clients for hosted CheLaile `/v1/search`, `/v1/stops/nearby`, `/v1/stops/detail`, `/v1/lines/detail`, `/v1/lines/realtime` and `/v1/health`, plus public Hong Kong operator requests and optional AMap base data. It contains no backend source, durable subscription storage, authenticated activity registration endpoint, APNs signing configuration or worker queue. The hosted API is useful as an upstream mainland data adapter; its current client contract is not an ActivityKit push service. A serverless request handler by itself is insufficient for reliable 30–60 second subscription work. Hong Kong and mainland identities must remain separate, and AMap base data cannot become CheLaile realtime without a verified mapping.

The upstream backend was also inspected at `37cdb4edec8a3120219b97b396ded83fc2b297b4` (rechecked 2026-10-13; unchanged): its [HTTP server](https://github.com/Justintunsday/chelaile-api-server/blob/37cdb4edec8a3120219b97b396ded83fc2b297b4/src/api/server.ts) registers query endpoints, with no activity registration routes. The [Cloudflare Worker](https://github.com/Justintunsday/chelaile-api-server/blob/37cdb4edec8a3120219b97b396ded83fc2b297b4/worker/index.ts) exposes a fetch handler; [wrangler configuration](https://github.com/Justintunsday/chelaile-api-server/blob/37cdb4edec8a3120219b97b396ded83fc2b297b4/worker/wrangler.toml) has no durable subscriptions, queues or scheduled triggers. The [Bun container](https://github.com/Justintunsday/chelaile-api-server/blob/37cdb4edec8a3120219b97b396ded83fc2b297b4/Dockerfile) starts the HTTP API only. These are source observations, not an audit of private production configuration.

The backend is suitable for reusing its provider adapter and query models, but needs a new durable subscription/scheduling layer and APNs sender. Recommended deployment: a separate worker process with persistent storage next to the Bun API, reusing its adapter; keep the public Worker/Vercel routes stateless. Alternatively extend the Cloudflare deployment with durable state and scheduling plus a verified APNs delivery path. Neither architecture is implemented or deployed by this PR.

Deploy a durable worker next to the existing API, or a separate service using that API. Provider authorization, upstream rate limits and operational hosting must be confirmed by the service owner. An APNs signing key, team ID and key ID remain server-side secrets, never application resources or committed fixtures.

## Proposed registration contract (not deployed)

`PUT /v1/live-activities/{activityID}` receives an authenticated, expiring subscription containing the ActivityKit update token, APNs environment (sandbox/production), exact `BusTrackingTarget`, creation time and expiry (at most one hour). Validate the provider's route, bound, service and station identity server-side; never trust a client-supplied URL. The activity ID is the idempotent subscription key, scoped to the authenticated installation; return HTTP 204 on success. `DELETE` revokes it on manual end. Apply per-installation limits, token encryption, TTL cleanup and log redaction. Token rotation replaces the previous token atomically.

The client implementation is `HTTPBusActivityPushRegistrar` plus `BusActivityPushCoordinator`. It uses HTTPS, a fresh bearer authorization closure for every request, PUT/DELETE, all per-activity `pushTokenUpdates` emissions, replacement of obsolete token work, bounded registration retry (0/1/2/4/8/16 seconds), and durable revoked IDs for retry after relaunch. Only IDs are stored in preferences; tokens remain in memory and are reacquired from ActivityKit. Foreground reconciliation restores observers and retries pending work. HTTP 404/410 on DELETE means already revoked; other failures remain pending.

After deployment, enable the Push Notifications capability for the host signing profile and inject the registrar at `AppState(activityRegistrar:)`. The manager then requests `.token` and installs token observers. Keep the default nil-registrar path for builds without a service. The Lock Screen end intent ends the system activity immediately; durable known IDs allow server revocation when the host reconciles again, with server TTL as the suspended-app safety net. Do not collect push-to-start tokens: this feature is deliberately started by a user choosing a trip in the app. No `UIBackgroundModes=remote-notification` is needed merely for ActivityKit APNs updates. Add frequent-update support only if justified; check `frequentPushesEnabled`, and do not promise an exact delivery cadence.

## Worker and APNs

Group subscriptions by the full canonical transit query and locale, not route number. Fetch authorized providers once per query, fan out predictions, throttle unchanged values and use a monotonic last-sent timestamp. A successful revised prediction replaces `arrivalEpoch`. A successful empty response sends `noService` and an end event; explicit cancellation, arrival/departure without a successor, or permanently invalid identity sends an end event. A transport failure sends `networkError`; a provider/API error sends `unavailable`, both retaining the last successful `updatedEpoch` and clock history, and invalidating `validUntilEpoch`. Neither resets freshness. New future departures use `secondArrivalEpoch` when present, `change: adjusted|nextBus` for that update, and `updateSource: push`. Expired subscriptions receive an end event. Revoke on APNs 410; back off 429/5xx; re-register rotated tokens. Use priority 5 normally and priority 10 only for meaningful urgent changes, within Apple's budget.

HTTP/2 headers:

```
apns-push-type: liveactivity
apns-topic: app.hkbus.swiftui.push-type.liveactivity
apns-priority: 5
authorization: bearer <short-lived provider JWT>
```

Send to `https://api.sandbox.push.apple.com/3/device/{activityUpdateToken}` for development or the production APNs host for production. An update example is in `activity-push-example.json`. All content dates are Unix seconds, matching the exact Codable contract. `stale-date` equals `validUntilEpoch`. An end event uses `event: end`, a full final content state (`status: ended` or `cancelled`, `arrivalEpoch: null`), and an appropriate `dismissal-date`. No persistent countdown survives a cancellation. Never log tokens or provider credentials.

## Concrete deployment plan (server components still to implement)

Use the existing Bun HTTP API for CheLaile requests, a PostgreSQL subscription store and a separate always-running worker in the same region. A one-minute serverless cron alone is not a promise of low-latency updates. Do not implement background URLSession polling in the iOS app as a substitute.

1. Add an authenticated installation-session issuer and PUT/DELETE registration routes to a separate service or the Bun API. Bind the installation identity to bearer sessions; apply one-active-trip limits. The iOS registrar obtains renewable credentials from that session provider, not a committed API key. Validate each exact provider/region/line/bound/service/stop query against upstream metadata before accepting it. Reject unsupported AMap realtime identities.
2. Apply the schema in `activity-subscriptions.sql` to a private PostgreSQL database. Encrypt ActivityKit tokens with a secret-manager key before storage; store no credentials in route JSON. DELETE writes a tombstone, not just row removal: an in-flight old PUT must never resurrect a stopped trip. Preserve tombstones until subscription expiry plus a cleanup interval. Rotation atomically replaces the token and increments generation.
3. Implement a worker that leases due rows with `FOR UPDATE SKIP LOCKED`, groups by server-generated canonical query hash, calls the appropriate HK/CheLaile adapter, normalizes results using the same state contract, and sends APNs HTTP/2 updates. Fetch every 30–60 seconds only where upstream authorization/rate limits permit; fan out once per query. Send updates on changed information or to renew a still-valid prediction before 90-second staleness. APNs delivery is budgeted and not guaranteed at this cadence. Cap retries and use jitter under failure. End at the stored one-hour expiry.
4. Provision PostgreSQL, one API process and one worker process on an always-running container host. Put TLS termination in front of the API; keep database and worker private. Inject `DATABASE_URL`, `TOKEN_ENCRYPTION_KEY`, `INSTALLATION_SESSION_SIGNING_KEY`, `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY_FILE`, `APNS_TOPIC=app.hkbus.swiftui.push-type.liveactivity`, and the authorized CheLaile upstream URL using the host's secret manager. Mount the APNs `.p8` file read-only. Keep sandbox and production queues separate, selected from the signed installation environment.
5. Configure health checks separately: API readiness, worker last-successful lease, provider failures, APNs 410/429/5xx counts, queue delay and expired-row cleanup. Redact tokens, authorization headers and precise stop identities from logs. Drain leases before deployments; expiration/revocation must not depend on one process staying alive.
6. Sign the host with Push Notifications enabled, inject `HTTPBusActivityPushRegistrar(endpoint: ..., environment: ..., scopeID: ..., authorization: ...)` into `AppState`, then validate the complete signed-device lifecycle and both APNs environments before changing the release disclosure. The current unsigned IPA deliberately keeps the nil registrar.

The SQL schema and client are supplied; the session issuer, registration handlers, worker/APNs sender, provider permissions, secrets and hosted deployment are **not implemented/deployed**. The repository does not claim end-to-end remote updates. Service bring-up requires implementing those components and passing the device gates below.

## Required deployment/device gates

1. Sign the host and extension under the same team, retaining the host bundle ID and a prefixed extension bundle ID; confirm embedded extension installation.
2. On iOS 17 and iOS 26, start/replace/end/restore/dismiss activities and test device settings disabling activities.
3. On hardware with and without Dynamic Island, inspect locked, expanded, compact, minimal, Always-On and stale presentations; test the end intent and cold-start regional deep link.
4. Suspend/terminate the app: the current implementation must become stale and must not claim updated predictions.
5. After the server is deployed, test token rotation, APNs sandbox/production separation, changed ETA, cancelled service, upstream failure, expiry, throttling and revocation. Remote updates cannot be marked complete before these pass.
